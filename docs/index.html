An AI coding agent says it fixed the bug. Expectrail plays the game and watches to find out.

It replays the changed game, has Meta's vision models find what each plain-English check names in the frames, and measures that against the engine's own record. The change is accepted only if every check passes, and the agent can't change the checks.

How it works

A person writes what the player should see. Plain code, not a model, decides whether the check passes.

  1. Play

    A harness replays a fixed route through the changed game and captures every frame, the same way every time.

  2. See

    SAM 3.1, or the open-weight Muse Glimmer, finds what the check names. The engine logs where things really are.

  3. Decide

    A deterministic evaluator compares the two. A missing or uncertain observation is "needs review", never a pass.

  4. Fix

    Muse Code gets a plain bug report and patches the game in a sandbox. If an attempt fails, the next one gets Expectrail's evidence; the two sinking bugs needed it.

  5. Hand over

    Every check passes on public and private routes, or nothing ships. A signed release candidate waits for a person.

What the fixer can reach

  • The game's editable files, in its own worktree
  • The bug report: the failing check's sentence, screenshots, the route and its log
  • After a failed attempt, Expectrail's evidence: the failing check's approved spec (read-only), the verdict and the first failing frame

In the live runs Muse Code works inside bubblewrap with only its worktree mounted; without bubblewrap it falls back to a plain worktree. It keeps network access to reach Meta's API and shares the host's kernel, so this is a boundary by absence, not a VM.

Kept out of its reach

  • The held-out bugs, the private routes, and why a guard failed
  • The evaluator's code, and write access to any check
  • The key that signs a release

If the vision model doesn't answer, the same candidate is judged again (unless the key was refused or is out of credit), then by Glimmer checked against the engine. It is never sent back to the fixer. When Glimmer decides, the report says so, because the ground is then judged on the engine's log alone.

Seven Meta models, and what each does

The models look, write and fix. None of them decides whether a change passes.

  • SAM 3.1Finds what a check names in the frames of a replay: the robot, the coins, the checkout button.
  • Muse Glimmer 30B open weightsJudges the vision checks with no SAM key, its boxes checked against the engine. Its boxes are too loose for the ground check, which then uses the engine's log. Also the fallback when SAM doesn't answer.
  • Muse SparkTurns a one-sentence check into a test spec that a person approves once, and sorts playtest remarks into draft checks.
  • Muse Spark Open open weightsThe same two jobs on open weights, served on Baseten.
  • Muse CodeThe fixer. It patches the game in a sandbox, and can neither change the checks nor see the held-out ones.
  • Muse WonderTriage: turns failure evidence into a bug report and a repair request.
  • Muse Voice TranscribeTurns a recorded playtest into who said what. Raw speech never becomes a check, and a request to switch one off is refused and queued for a person.

Why open weights matter here: an unreleased game build is confidential. With Glimmer, the vision checks could run on a studio's own hardware; so far we have run it only on a Fireworks deployment. How we use them

What it can't do yet

  • It checks a change; it doesn't explore. It replays fixed routes, so a bug where no route goes is invisible to it.
  • It checks only what someone described. Three approved checks guard the game today.
  • One game and one web page. Mostly with bugs we seeded. A teammate wrote the game's held-out bugs; the page's private bugs came from an AI agent of the same model family that tuned its checks.
  • The sandbox isn't a hard boundary. The fixer has network access and shares the host's kernel.
